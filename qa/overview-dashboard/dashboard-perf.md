# เวลาตอบของหน้าภาพรวม (`GET /dashboard`) — task 2.6 ของ `overview-dashboard`

**วันที่วัด:** 2026-11-01 · **เครื่อง:** โน้ตบุ๊ก dev เครื่องเดียวกับที่วัดรายงาน (Windows 10 + Docker ใน WSL, RAM 8 GB, PostgreSQL 16 ค่าเริ่มต้น) ขณะ stack ของ SDES รันอยู่ด้วย

**เกณฑ์:** ข้อมูลทั้งหน้าตอบภายใน 1 วินาทีที่ปริมาณ 12 เดือนตาม BRD (spec overview-dashboard "Freshness and performance")

## ข้อมูล

ฐาน `sdes_perf` ชุดเดียวกับที่วัดรายงาน (`Service/load/reports-perf-seed.sql`): เอกสาร 42,000 ฉบับ (12 เดือน × 3,500), ประวัติสถานะ 210,000 แถว ณ วันที่วัด มีเอกสารที่อัปโหลดในช่วง 14 วันล่าสุด 1,495 ฉบับ และ 7 วันล่าสุด 690 ฉบับ จึงมีข้อมูลจริงในทุกช่วงที่หน้าภาพรวมคำนวณ

ผู้ใช้ที่วัดมี role `AP_LEAD` + `FINANCE_EXEC` + `SYS_ADMIN` จึงได้ครบทุกส่วน (`backlog, throughput, indicators, finance, health` รวม error 24 ชั่วโมงและ API key ใกล้หมดอายุ) = กรณีที่หนักที่สุด

## ผล (ms, วัดผ่าน HTTP กับ api ที่ build แล้ว — `node Service/load/dashboard-perf.mjs`, 11 คำขอต่อรอบ)

| รอบ | ครั้งแรก | ค่ากลาง (10 ครั้งถัดไป) | สูงสุด |
|---|---|---|---|
| 1 | 425 | 186 | 251 |
| 2 | 219 | 230 | 246 |
| 3 | 301 | 260 | 308 |

**ผล: ผ่าน** — ค่ากลาง 186–260 ms และสูงสุด 425 ms (คำขอแรกหลังเปิด api) ต่ำกว่าเกณฑ์ 1 วินาทีมาก จึงยังไม่เพิ่ม index `document_status_history (to_status, created_at)` ตามที่ design D3 เผื่อไว้

## ข้อสังเกตสำหรับ Phase 4

- หน้าภาพรวมดึงใหม่ทุก 30 วินาทีต่อผู้ใช้ที่เปิดหน้าค้าง ที่ 50 คนพร้อมกันคือ ~1.7 คำขอต่อวินาที × ~0.25 วินาที ≈ 0.4 วินาทีของ CPU ฐานข้อมูลต่อวินาที — บน hosting ฟรีที่ CPU น้อยกว่า ควรวัดซ้ำและพิจารณา cache ผลลัพธ์สั้น ๆ (เช่น 10–15 วินาทีต่อชุดสิทธิ์)
