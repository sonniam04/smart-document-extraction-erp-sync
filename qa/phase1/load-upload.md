# Load test: อัปโหลดพร้อมกัน 50 ไฟล์ (task 6.10)

- วันที่: 29/10/2569
- Repo: `sdes-service` branch `feat/phase1-foundations`
- สคริปต์: `Service/load/upload.k6.js` (วิธีรันอยู่ใน `Service/load/README.md`)
- สภาพแวดล้อม: dev stack ใน Docker บน WSL2 (RAM 8 GB, 12 CPU)
  - api 1 instance (สแกนพร้อมกันได้ 4 ไฟล์ต่อคำขอ)
  - worker 1 instance (concurrency 2)
  - ClamAV ตั้งค่าเริ่มต้น
  - SeaweedFS และ PostgreSQL 16
- ข้อมูล: ไฟล์ byte สุ่มขนาด 5 MB ขึ้นต้นด้วย `%PDF-1.7` (ไม่ใช่เอกสารจริง)

## ผล

| ตัวชี้วัด | ผล | เกณฑ์ |
|---|---|---|
| คำขอที่ได้ 201 และได้เลขเอกสาร | **50/50** | 50/50 (spec: Concurrent upload capacity) |
| HTTP error | 0% | 0% |
| เอกสารที่ประมวลผลจนเป็น `EXTRACTED` | 50/50 | ทุกฉบับเข้าคิวและไม่หาย |
| เวลาตอบ ขณะยิงพร้อมกัน 50 ไฟล์ | เฉลี่ย 9.08 s, p95 11.25 s, สูงสุด 11.26 s | — |
| เวลาตอบ อัปโหลดทีละไฟล์ 5 MB (วัด 3 ครั้ง) | 0.45 / 0.52 / 0.50 s | ≤ 5 s ไม่นับเวลาส่งไฟล์ (spec: Processing hand-off) |
| ข้อมูลที่ส่ง | 262 MB ใน ~12.7 s | — |

**สรุป:** ผ่านเกณฑ์ทั้งสองข้อ คือรับได้ 50 ไฟล์พร้อมกันโดยไม่มีไฟล์ล้มเหลว และอัปโหลดปกติตอบภายใน 5 วินาที

## ข้อสังเกต

- **เวลาตอบตอนโหลดหนักส่วนใหญ่มาจากการรอคิวสแกนของ ClamAV**
  - เวลารวมขณะยิงพร้อมกันรวมทั้งการส่งไฟล์ 5 MB และการรอ clamd ที่สแกนได้ทีละไม่กี่ไฟล์
  - อัปโหลดเดี่ยวใช้เวลา 0.5 s ซึ่งรวมการสแกนแล้ว
- **ปริมาณจริงตาม BRD ต่ำกว่าที่ทดสอบมาก:** 3,500 ฉบับ/เดือน เฉลี่ยราว 20 ฉบับต่อชั่วโมงทำการ
- **ถ้าใน Phase 4 ต้องการให้ตอบเร็วขึ้นตอนโหลดหนัก มี 2 ทาง:**
  - เพิ่ม `MaxThreads` ของ clamd
  - เปลี่ยนเป็น "รับไฟล์ → สแกนใน worker" (ตอบทันทีแล้วแจ้งผลสแกนทีหลัง) แต่ทางนี้ต้องแก้ spec เพราะ spec กำหนดให้สแกนก่อนจัดเก็บถาวร
- **ข้อจำกัดของการทดสอบ:** ยิงจาก container ใน network เดียวกัน จึงไม่รวม latency ของเครือข่ายจริงระหว่างผู้ใช้กับ server
