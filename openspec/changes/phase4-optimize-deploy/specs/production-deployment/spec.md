# Spec Delta

## Purpose

กำหนดพฤติกรรมของระบบเมื่อรันบนเครื่อง production: ทางเข้าเดียวผ่าน HTTPS, การจัดการค่าตั้งและ secret, การทำงานต่อเนื่องเมื่อ service ล้มหรือเครื่องรีบูต, การ deploy และย้อนเวอร์ชัน, การสำรองและกู้คืนข้อมูล, งบทรัพยากร และเกณฑ์ประสิทธิภาพบนเครื่องจริง

## ADDED Requirements

### Requirement: Single HTTPS entry point
บนเครื่อง production ระบบ SHALL รับคำขอจากภายนอกผ่าน reverse proxy ตัวเดียวเท่านั้น โดยให้บริการด้วย HTTPS ที่ใบรับรองต่ออายุอัตโนมัติ คำขอ HTTP MUST ถูกพาไป HTTPS และ api, ฐานข้อมูล, Redis, ที่เก็บไฟล์ และตัวสแกนไวรัส MUST เข้าถึงจากภายนอกเครื่องไม่ได้

#### Scenario: เปิดผ่าน HTTP
- **WHEN** ผู้ใช้เปิด `http://<โดเมน>/login`
- **THEN** ได้ redirect ไป `https://<โดเมน>/login` และหน้าเว็บโหลดด้วยใบรับรองที่ browser เชื่อถือ

#### Scenario: เรียกฐานข้อมูลจากภายนอก
- **WHEN** มีการเชื่อมต่อจากอินเทอร์เน็ตไปยัง port ของ PostgreSQL, Redis, S3, ClamAV หรือ api ของเครื่อง production
- **THEN** การเชื่อมต่อถูกปฏิเสธหรือหมดเวลา

### Requirement: Configuration and secrets
ค่าตั้งของ production SHALL อยู่ในไฟล์บนเครื่อง production เท่านั้น สร้างด้วยค่าสุ่มที่ปลอดภัยและอ่านได้เฉพาะผู้ดูแล secret MUST ไม่อยู่ใน repo, image หรือ log api และ worker SHALL ตรวจค่าที่จำเป็นตอนเริ่ม ถ้าขาดหรือไม่ถูกต้อง MUST หยุดทำงานพร้อมข้อความที่ระบุชื่อค่าที่มีปัญหา โดยไม่แสดงค่าของ secret

#### Scenario: ลืมตั้งค่า
- **WHEN** เริ่ม api บน production โดยไม่มีค่า secret ของ JWT
- **THEN** api ไม่เริ่มรับคำขอ และ log ระบุชื่อค่าที่ขาด

#### Scenario: ตรวจ image
- **WHEN** ค้นหารหัสผ่านฐานข้อมูลหรือ secret ใด ๆ ในชั้นของ image ที่ build แล้ว
- **THEN** ไม่พบ

### Requirement: Self-healing services
ทุก service บน production SHALL เริ่มใหม่เองเมื่อหยุดผิดปกติและเมื่อเครื่องรีบูต และ SHALL มี health check ที่สะท้อนความพร้อมจริง service ที่ต้องพึ่งพาตัวอื่น MUST เริ่มหลังจากตัวที่พึ่งพาพร้อมแล้ว

#### Scenario: worker ล้ม
- **WHEN** process ของ worker หยุดทำงานผิดปกติ
- **THEN** worker เริ่มใหม่เองและงานในคิวทำต่อโดยไม่มีงานหาย

#### Scenario: เครื่องรีบูต
- **WHEN** เครื่อง production รีบูต
- **THEN** ระบบกลับมาใช้งานได้โดยไม่ต้องมีคนสั่ง และข้อมูลเดิมอยู่ครบ

### Requirement: Repeatable deploy and rollback
การ deploy SHALL ทำได้ด้วยคำสั่งเดียวที่ระบุเวอร์ชัน (git ref) โดย migrate ฐานข้อมูลก่อน api เริ่มรับคำขอ และถือว่าสำเร็จเมื่อ health check ของทุก service ผ่าน ถ้าไม่ผ่าน MUST คงเวอร์ชันเดิมทำงานต่อหรือย้อนกลับได้ด้วยคำสั่งเดียว การ deploy MUST ไม่ทำให้ข้อมูลหาย

#### Scenario: deploy เวอร์ชันใหม่
- **WHEN** ผู้ดูแลสั่ง deploy เวอร์ชันใหม่ที่มี migration
- **THEN** migration ถูกใช้ก่อน api ใหม่รับคำขอ และเอกสารที่มีอยู่ยังเปิดได้หลัง deploy

#### Scenario: เวอร์ชันใหม่เริ่มไม่ขึ้น
- **WHEN** api ของเวอร์ชันใหม่ไม่ผ่าน health check ภายในเวลาที่กำหนด
- **THEN** คำสั่ง deploy รายงานว่าล้มเหลว และคำสั่งย้อนกลับพาระบบกลับไปเวอร์ชันก่อนหน้าที่ใช้งานได้

### Requirement: Backup and restore
ระบบ SHALL สำรองฐานข้อมูลและไฟล์เอกสารอัตโนมัติวันละครั้ง เก็บอย่างน้อย 7 ชุดล่าสุด และ SHALL มีขั้นตอนกู้คืนที่ทำให้ระบบกลับมาพร้อมเอกสาร ไฟล์ และ audit trail ครบตามชุดที่เลือก ไฟล์สำรอง MUST ไม่อยู่ใน volume เดียวกับข้อมูลที่ใช้งาน

#### Scenario: กู้คืนบนเครื่องใหม่
- **WHEN** ผู้ดูแลกู้คืนชุดสำรองล่าสุดบนเครื่องใหม่ที่ติดตั้งตามคู่มือ
- **THEN** ผู้ใช้ล็อกอินได้ เอกสารเดิมเปิดพร้อมไฟล์ต้นฉบับได้ และ audit trail ครบเท่ากับตอนสำรอง

#### Scenario: เก็บครบ 7 ชุด
- **WHEN** การสำรองรันครบวันที่ 8
- **THEN** ชุดที่เก่าที่สุดถูกลบ และเหลือ 7 ชุดล่าสุด

### Requirement: Resource budget
ผลรวมของ RAM ที่จัดให้ทุก service บน production SHALL ไม่เกิน 80% ของ RAM เครื่อง แต่ละ service MUST มีเพดาน RAM ของตัวเอง เพื่อให้ service หนึ่งใช้หน่วยความจำเกินแล้วไม่ทำให้ตัวอื่นล้ม

#### Scenario: ตรวจงบ
- **WHEN** ระบบทำงานตามปกติบนเครื่องที่มี RAM 12 GB
- **THEN** เพดาน RAM รวมของทุก service ไม่เกิน 9.6 GB และไม่มี service ใดถูกระบบปฏิบัติการปิดเพราะหน่วยความจำไม่พอระหว่างการทดสอบ

### Requirement: Performance on the production host
บนเครื่อง production ข้อมูลหน้าภาพรวมและรายงาน 12 เดือนที่ปริมาณตาม BRD (3,500 ฉบับต่อเดือน) SHALL ตอบภายใน 1 วินาทีที่ค่ากลาง และหน้าเว็บ SHALL โหลดหน้าแรกหลังล็อกอินเสร็จภายใน 3 วินาทีบนการเชื่อมต่อบรอดแบนด์ การวัด MUST ใช้ฐานข้อมูลแยกที่ไม่ใช่ข้อมูลจริง

#### Scenario: วัดหลัง deploy
- **WHEN** รันสคริปต์วัดของหน้าภาพรวมและรายงานกับฐาน perf บนเครื่อง production
- **THEN** ค่ากลางของทั้งสองต่ำกว่า 1 วินาที และผลถูกบันทึกพร้อมสเปกเครื่อง
