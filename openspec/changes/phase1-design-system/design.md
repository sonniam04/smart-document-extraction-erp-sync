# Design

## Context

`sdes-web` ยังว่างอยู่ ผู้ใช้หลักคือ AP Clerk ที่ตรวจเอกสารวันละหลายสิบถึงหลักร้อยใบ, AP Lead ที่ตัดสินเคสเสี่ยง และผู้บริหารที่ดูภาพรวม ทั้งหมดเป็นงานแบบ **Operate** (ผู้ใช้ต้องทำงานให้เสร็จ) ไม่ใช่หน้าขายของ ความเร็วในการอ่าน ความถูกต้องของตัวเลข และความสม่ำเสมอจึงสำคัญกว่าความหวือหวา องค์กรไม่ได้ระบุแบรนด์ (ดู proposal) Stack ถูกกำหนดแล้ว: Next.js App Router + Tailwind CSS

## Goals / Non-Goals

**Goals:**
- Token ชุดเดียวเป็นแหล่งความจริงของทุกค่าที่มองเห็นได้ เพื่อให้เปลี่ยนแบรนด์ภายหลังได้ที่จุดเดียว
- Component ที่ครอบคลุมหน้าจอ Phase 1–2 ทั้งหมด พร้อม state ครบ (ปกติ, hover, focus, disabled, loading, error)
- Wireframe ของหน้าอัปโหลด/คิว และหน้า split-view ที่ผู้ใช้อนุมัติแล้ว ก่อน Phase 2 เริ่ม

**Non-Goals:**
- Dark mode (โครง token รองรับ แต่ยังไม่ออกแบบหรือทดสอบ)
- Animation ที่ไม่ได้สื่อความหมาย
- Component library แยกเป็น package (มีแอปเดียว จึงยังไม่คุ้ม)

## Decisions

### D1. ใช้ skill Impeccable เป็นกระบวนการออกแบบ
- `init` เพื่อสร้าง `PRODUCT.md` (ผู้ใช้, งาน, บริบทการใช้งาน), `shape` สำหรับ 2 หน้าหลัก และเขียน `DESIGN.md` เป็นภาษาภาพของระบบ
- ใช้ `audit` (a11y, responsive) และ `critique` ตรวจก่อนปิดงาน
- **เหตุผล:** ได้หลักการที่บันทึกไว้ถาวร ให้ทุก phase ต่อจากนี้ทำตามได้ แทนการตัดสินใจกระจัดกระจายในโค้ด

### D2. Token เป็น CSS custom properties และ map เข้า Tailwind
- ไฟล์ `Web/src/styles/tokens.css` ประกาศ `--color-*`, `--space-*`, `--radius-*`, `--font-*` บน `:root` ส่วน `tailwind.config` อ้างถึงตัวแปรเหล่านี้ ห้ามใส่ค่าสี/ระยะตรง ๆ ใน component
- ชั้นของ token: primitive (สเกลสี) → semantic (`--color-surface`, `--color-text-muted`, `--color-status-synced-bg`) → component ใช้เฉพาะ semantic
- **ทางเลือกที่ไม่เลือก:** ค่าตายตัวใน `tailwind.config` (เปลี่ยนเป็นแบรนด์หรือ dark mode ยากกว่า), CSS-in-JS (ไม่เข้ากับ React Server Components)

### D3. Typography
- โลกของภาพที่ผู้ใช้เลือก (Impeccable direction round 2026-10-29) คือ **"แบบฟอร์มกรมสรรพากร"** ตัวหลักจึงเป็น **Sarabun** ซึ่งเป็นฟอนต์มาตรฐานเอกสารราชการไทยที่ฝ่ายบัญชีอ่านทุกวัน มีทั้งไทยและละติน โหลดผ่าน `next/font` เป็น self-host
- ตัวเลขจำนวนเงิน: บังคับ `font-variant-numeric: tabular-nums` หาก Sarabun ไม่มี tabular figures ที่ใช้งานได้ ให้ใช้ฟอนต์ตัวเลขสำรองที่ความกว้างเท่ากันเฉพาะคอลัมน์จำนวนเงิน (ตรวจในงาน 2.2)
- line-height ของข้อความไทยไม่ต่ำกว่า 1.6 เพื่อไม่ให้สระบน/ล่างชนกัน
- **ทางเลือกที่ไม่เลือก:** IBM Plex Sans Thai (ร่างเดิม แต่บุคลิกไม่เข้ากับโลกแบบฟอร์มที่เลือก), Noto Sans Thai + Inter (สองตระกูลที่บุคลิกไม่เข้ากัน)

### D4. สีและสถานะ
- ชุดสีของโลกแบบฟอร์มภาษี:
  - **น้ำเงินหมึกพิมพ์** `#1B2B4B` เป็นสีของแถบบน เส้นแบ่งหมวด และปุ่มหลัก (สีน้ำเงินนี้ใช้กับสิ่งที่กดได้เท่านั้นในพื้นที่ทำงาน)
  - **ฟ้าแบบฟอร์ม** `#E8EEF7` เป็นพื้นของ shell
  - **กระดาษขาว** เป็นพื้นของพื้นที่ทำงาน
  - **แดงตรายาง** `#B42318` สงวนไว้ให้ความเสี่ยงและจุดที่ต้องตรวจ
- จุดเด่นประจำระบบ: ฟอร์มแบ่งเป็นหมวดมีเลขกำกับ, Tax ID แสดงในช่องทีละหลัก (กลุ่ม 1-4-5-2-1), ยอดเงินเป็นแถวที่มีเส้นประนำสายตาไปยังตัวเลขชิดขวา ไม่ลอกแบบฟอร์มราชการตรงตัว (ไม่มีตราครุฑหรือหัวกระดาษราชการ) และไม่ตีกรอบทุก field
- แบ่งสีสถานะ 11 สถานะเป็น 5 กลุ่มความหมาย และแต่ละสถานะมีไอคอนของตัวเอง:
  - กำลังดำเนินการ: `UPLOADED`, `PROCESSING`, `SYNCING`
  - รอคน: `EXTRACTED`, `VERIFIED`, `PENDING_APPROVAL`
  - สำเร็จ: `APPROVED`, `SYNCED`
  - ล้มเหลว: `FAILED`, `SYNC_FAILED`
  - ยุติ: `REJECTED`
- Confidence 3 ระดับใช้สเกลเดียวกับกลุ่ม "รอคน/ล้มเหลว" ไม่สร้างสีใหม่
- ทุกคู่สีข้อความ/พื้นต้องผ่าน contrast 4.5:1 ตรวจด้วยสคริปต์ในงาน 2.3

### D5. ความหนาแน่น
- ผู้ใช้หลักทำงานบน **notebook จอเดียว** (ผู้ใช้ยืนยัน 2026-10-29) เป้าหมายจึงเป็นจอ 1366×768 โดยยังสวยที่ 1920×1080
- ใช้ความหนาแน่นแบบ "compact-comfortable": ความสูงแถวตาราง 36–40 px, ฟอนต์ข้อมูล 14 px, ฟอนต์ป้าย 12 px, เมนูอยู่แถบบน (ไม่ใช้แถบข้าง) เพื่อเก็บความกว้างให้ split-view
- split-view บน 1366×768: PDF ราว 55% ฟอร์ม 45% ฟอร์มเลื่อนแยกจาก PDF และแถบปุ่มล่างติดอยู่ตลอด ตาราง line items เห็นอย่างน้อย 8 แถวแล้วเลื่อนภายในตาราง
- **ทางเลือกที่ไม่เลือก:** ระยะห่างแบบ consumer app (แถว 56 px) ซึ่งทำให้ต้องเลื่อนมากเกินไปสำหรับงานตรวจทานต่อเนื่อง

### D6. ชุด component และที่อยู่
- `Web/src/components/ui/`: Button, TextField, AmountField, Select, DataTable, StatusBadge, ConfidenceBadge, BBoxOverlay, Dropzone, Toast, ConfirmDialog, EmptyState, ErrorState, Skeleton, AppShell
- ใช้ Radix UI primitives เป็นฐานของ Dialog/Select/Toast เพื่อให้ได้พฤติกรรมคีย์บอร์ดและ ARIA ที่ถูกต้องโดยไม่เขียนเอง แล้วจัดสไตล์ด้วย token
- `AmountField` เก็บค่าเป็น string ทศนิยมแล้วแปลงเป็น `Decimal` ตอนส่ง ไม่ผ่าน `number` เพื่อไม่ให้เกิดความคลาดเคลื่อนของ float
- `BBoxOverlay` รับพิกัดเป็นสัดส่วน (0–1) ของหน้า PDF จึงไม่ขึ้นกับระดับการซูม
- ข้อความ UI รวมไว้ที่ `Web/src/i18n/th.ts` เพื่อให้แก้ไขและตรวจน้ำเสียงได้ที่เดียว (ยังไม่ทำระบบหลายภาษา)

### D7. หน้ารวม component
- Route `/dev/components` ที่ build เฉพาะเมื่อ `NODE_ENV !== 'production'` แสดงทุก component ในทุก state และเป็นเป้าของการตรวจ accessibility อัตโนมัติ (axe ผ่าน Playwright)
- **ทางเลือกที่ไม่เลือก:** Storybook (เพิ่ม dependency และ build อีกชุดที่ต้องดูแล ทั้งที่มีแอปเดียว)

### D8. Wireframe
- ทำเป็นหน้า HTML ความละเอียดกลาง (ใช้ token จริง แต่ใช้ข้อมูลจำลอง) และส่งให้ผู้ใช้รีวิว 2 หน้า: อัปโหลด/คิว และ split-view (PDF + bbox ซ้าย, ฟอร์ม header + ตาราง line items + สรุปยอดชั้น 1/ชั้น 2 ขวา)
- ข้อมูลจำลองต้องไม่ใช่ข้อมูลลูกค้าจริง

## Risks / Trade-offs

- [ไม่มีแบรนด์องค์กร ทำให้ภายหลังอาจต้องเปลี่ยนโทน] → token แบบสองชั้นทำให้การเปลี่ยนแบรนด์แก้แค่ primitive และ semantic mapping
- [IBM Plex Sans Thai อาจมี tabular figures ไม่สมบูรณ์] → งาน 2.2 ตรวจด้วยภาพจริง และมี IBM Plex Mono สำรองสำหรับคอลัมน์จำนวนเงิน
- [Wireframe ถูกปรับระหว่างรีวิวจนกระทบ component] → ทำ wireframe (กลุ่ม 1) ให้เสร็จและได้รับอนุมัติก่อนสร้าง component ที่ซับซ้อน (DataTable, BBoxOverlay)
- [Radix เพิ่ม dependency] → ใช้เฉพาะ primitive ที่จำเป็น และ tree-shake ได้
