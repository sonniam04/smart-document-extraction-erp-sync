# Proposal

## Why

หลัง Phase 2 เอกสารถูกอ่าน ตรวจ และอนุมัติได้แล้ว แต่ยังหยุดอยู่ที่ `VERIFIED`/`APPROVED` ฝ่ายบัญชีจึงยังต้องคีย์ใบแจ้งหนี้ซื้อเข้า Odoo ด้วยมือ Phase 3 (สัปดาห์ที่ 6–7, 25% ตาม BRD ข้อ 9) ส่งข้อมูลที่ผ่านการตรวจแล้วเข้า ERP อัตโนมัติ (BRD FR-05) พร้อมจัดการความล้มเหลวตาม NFR Error Handling, เพิ่มเครื่องมือของ IT & System Auditor และปิดช่องโหว่ด้านความปลอดภัยก่อน UAT ใน Phase 4

## What Changes

- **ส่งเข้า Odoo อัตโนมัติ:** เอกสาร `VERIFIED` ที่ไม่มีความเสี่ยงและเอกสาร `APPROVED` ถูกส่งเป็นใบแจ้งหนี้ซื้อ (Vendor Bill) ใน Odoo พร้อมรายการสินค้า ภาษีซื้อ 7% และไฟล์ต้นฉบับแนบ แล้วเก็บเลขที่ของ Odoo กลับมา (`SYNCING → SYNCED`)
- **ไม่ส่งซ้ำ:** ส่งซ้ำด้วยเหตุใดก็ตาม (retry, กดส่งใหม่) ต้องไม่สร้างใบแจ้งหนี้ซ้ำใน Odoo
- **จัดการความล้มเหลว (NFR Error Handling):** ลองใหม่ 3 ครั้งแบบ exponential backoff เมื่อ Odoo ไม่ตอบสนอง ส่งไม่สำเร็จแล้วเป็น `SYNC_FAILED` และเข้าคิวที่ล้มเหลว (DLQ) ให้ System Admin ตรวจและสั่งส่งใหม่
- **ผู้ขายใน Odoo:** จับคู่ผู้ขายกับคู่ค้าใน Odoo ด้วยเลขประจำตัวผู้เสียภาษี + สาขา ถ้าไม่พบให้สร้างคู่ค้าใหม่
- **Generic webhook (ทางสำรอง):** ส่ง payload JSON ที่ลงลายเซ็น HMAC-SHA256 ไปยัง URL ที่ตั้งไว้ สำหรับ ERP อื่นในอนาคต
- **หน้าตั้งค่าการเชื่อมต่อ ERP (System Admin):** ชนิด adapter, URL, ฐานข้อมูล, API key (เก็บแบบเข้ารหัส ไม่แสดงกลับ), journal/ภาษี/บัญชีค่าใช้จ่ายเริ่มต้น, ปุ่มทดสอบการเชื่อมต่อ และเปิด/ปิดการส่งอัตโนมัติ
- **หน้าติดตามการส่ง (IT & System Auditor):** จำนวนเอกสารแต่ละสถานะ, รายการ `SYNC_FAILED` พร้อมเหตุผล, ประวัติการส่งรายครั้ง และส่งใหม่ทีละฉบับหรือทั้งชุด
- **หน้า Audit trail:** ค้นหาตามช่วงเวลา ผู้กระทำ ประเภท และเอกสาร สำหรับ Finance Exec และ System Admin พร้อมส่งออก CSV
- **ความปลอดภัย (RBAC Security):** จำกัดอัตราการเรียก login/อัปโหลด, security headers, เข้ารหัส secret ของการเชื่อมต่อ ERP ด้วย AES-256-GCM, สแกน dependency หาช่องโหว่ระดับ critical ใน CI และทดสอบสิทธิ์ทุก endpoint ตาม permission matrix อัตโนมัติ
- **E2E อัตโนมัติ (BRD Phase 3):** ชุด E2E กับ Odoo จริงใน docker ตั้งแต่อัปโหลดจนเห็น Vendor Bill ใน Odoo

นอกขอบเขต: การจ่ายเงินและหนังสือรับรองหัก ณ ที่จ่ายใน Odoo, การดึงข้อมูลกลับจาก Odoo (ซิงก์สองทาง), OIDC/SSO, production deployment (Phase 4), adapter เฉพาะของ SAP/Dynamics

### สมมติฐาน (ให้ผู้ใช้ยืนยันตอนรีวิว)

1. **Odoo ของบริษัทเป็นรุ่น 19 ขึ้นไป** ใช้ JSON-2 API (`/json/2/<model>/<method>` + API key) ซึ่งเป็นทางที่ Odoo แนะนำ; ถ้าเป็นรุ่น 17–18 ใช้ JSON-RPC (`/jsonrpc`) ผ่านตัวเลือกใน config — XML-RPC/JSON-RPC จะถูกถอดใน Odoo 22
2. **ผู้ขายที่ไม่มีใน Odoo ถูกสร้างเป็นคู่ค้าใหม่อัตโนมัติ** (ชื่อ, เลขประจำตัวผู้เสียภาษี, สาขา) แทนการให้ sync ล้มเหลว
3. **หัก ณ ที่จ่ายไม่ถูกบันทึกเป็นรายการในใบแจ้งหนี้ซื้อ** (Odoo บันทึกตอนจ่ายเงิน) แต่ส่งฐาน อัตรา ยอดหัก และยอดจ่ายสุทธิไปในหมายเหตุของใบแจ้งหนี้ เพื่อให้ผู้จ่ายเงินเห็น
4. **รายการสินค้าไม่ผูกกับสินค้าใน Odoo** ใช้บัญชีค่าใช้จ่ายเริ่มต้นที่ตั้งไว้ และรหัสภาษีซื้อ 7% ที่ตั้งไว้ (เอกสารยกเว้น VAT ไม่ใส่ภาษี)
5. **ใบแจ้งหนี้ใน Odoo ถูกสร้างเป็นร่าง (draft)** ไม่ post อัตโนมัติ ให้ฝ่ายบัญชีใน Odoo ตรวจ/post ตามขั้นตอนเดิม
6. **การส่งอัตโนมัติปิดไว้จนกว่า Admin จะทดสอบการเชื่อมต่อผ่าน** เอกสารที่พร้อมส่งระหว่างนั้นรออยู่ที่ `VERIFIED`/`APPROVED` และถูกส่งเมื่อเปิด

## Capabilities

### New Capabilities
- `erp-sync`: การส่งเอกสารที่ผ่านการตรวจเข้า ERP — เงื่อนไขการส่ง, ข้อมูลที่ส่ง, การกันส่งซ้ำ, retry/DLQ, การส่งใหม่, เลขที่อ้างอิงจาก ERP และ adapter ของ Odoo และ generic webhook
- `erp-connection`: การตั้งค่าและทดสอบการเชื่อมต่อ ERP โดย System Admin รวมถึงการเก็บ secret แบบเข้ารหัสและการเปิด/ปิดการส่งอัตโนมัติ
- `operations-monitoring`: หน้าติดตามคิวและการส่งสำหรับ System Admin/IT Auditor
- `platform-security`: การป้องกันระดับระบบ — จำกัดอัตรา, security headers, การสแกนช่องโหว่ และการทดสอบสิทธิ์ทุก endpoint

### Modified Capabilities
- `audit-trail`: เพิ่มหน้าจอค้นหาและส่งออก audit trail (เดิมมีเฉพาะ API ค้นหา)

## Impact

- `sdes-service`: `ErpAdapter` ใน `packages/core` ได้ implementation จริง (Odoo, webhook), คิว BullMQ `erp-sync` ใน worker, API ตั้งค่า ERP/ติดตามการส่ง/ส่งใหม่, migration (การตั้งค่าการเชื่อมต่อแบบเข้ารหัส, ผลการส่ง, เลขที่ใน ERP, รหัสคู่ค้าใน Odoo), rate limit + security headers, CI สแกนช่องโหว่
- `sdes-web`: หน้า `/admin/erp`, `/admin/sync`, `/audit` และสถานะการส่งในหน้าตรวจ/คิว
- Repo หลัก: ชุด E2E กับ Odoo ใน `qa/e2e`
- Dev stack: Odoo + PostgreSQL ของ Odoo ใน docker compose (profile `odoo` เปิดเมื่อต้องการ ใช้ RAM เพิ่มราว 1 GB)
- Secret ใหม่: `ERP_SECRET_KEY` (กุญแจเข้ารหัส secret ของการเชื่อมต่อ ERP) ใน `.env`
- ข้อมูลใบแจ้งหนี้และไฟล์ต้นฉบับถูกส่งเข้า Odoo ของบริษัทเอง (self-hosted) ไม่ออกนอกองค์กร
