# Spec Delta

## Purpose

กำหนดวิธีที่ผู้ใช้ยืนยันตัวตนเข้าสู่ระบบ SDES, role ที่มีในระบบ และสิ่งที่แต่ละ role ทำได้ เพื่อแยกหน้าที่ตามหลักควบคุมภายในของฝ่ายบัญชี

## ADDED Requirements

### Requirement: System roles
ระบบ SHALL มี role ทั้งหมด 4 แบบ: `AP_CLERK` (เจ้าหน้าที่บัญชีปฏิบัติการ), `AP_LEAD` (หัวหน้าฝ่ายบัญชี/ผู้อนุมัติ), `FINANCE_EXEC` (ผู้บริหารฝ่ายการเงิน), `SYS_ADMIN` (ผู้ดูแลระบบ) ผู้ใช้แต่ละคน MUST มีอย่างน้อยหนึ่ง role

#### Scenario: สร้างผู้ใช้โดยไม่ระบุ role
- **WHEN** System Admin สร้างบัญชีผู้ใช้โดยไม่เลือก role ใดเลย
- **THEN** ระบบปฏิเสธการสร้างและแจ้งว่าต้องเลือกอย่างน้อยหนึ่ง role

#### Scenario: ผู้ใช้หลาย role
- **WHEN** ผู้ใช้มีทั้ง role `AP_CLERK` และ `FINANCE_EXEC`
- **THEN** ผู้ใช้ได้รับสิทธิ์รวมของทั้งสอง role

### Requirement: Permission matrix
ระบบ SHALL อนุญาตการกระทำตาม role ดังนี้: `AP_CLERK` อัปโหลด ดู และแก้ข้อมูลเอกสาร; `AP_LEAD` ทำได้เท่า `AP_CLERK` และอนุมัติ/ปฏิเสธเคสเสี่ยง; `FINANCE_EXEC` ดูเอกสาร รายงาน และ audit trail แบบอ่านอย่างเดียว; `SYS_ADMIN` จัดการผู้ใช้ การตั้งค่าระบบ API keys และการเชื่อมต่อ ERP การกระทำที่ role ไม่มีสิทธิ์ MUST ถูกปฏิเสธที่ฝั่ง server

#### Scenario: Finance Exec พยายามแก้ข้อมูล
- **WHEN** ผู้ใช้ที่มีเพียง role `FINANCE_EXEC` ส่งคำขอแก้ field ของเอกสาร
- **THEN** ระบบตอบกลับว่าไม่มีสิทธิ์ (403) และไม่มีข้อมูลใดถูกเปลี่ยน

#### Scenario: Clerk พยายามจัดการผู้ใช้
- **WHEN** ผู้ใช้ role `AP_CLERK` เรียก API สร้างผู้ใช้
- **THEN** ระบบตอบกลับ 403

#### Scenario: Admin ไม่ได้รับสิทธิ์งานบัญชีโดยอัตโนมัติ
- **WHEN** ผู้ใช้ที่มีเพียง role `SYS_ADMIN` พยายามอัปโหลดหรือแก้ข้อมูลเอกสาร
- **THEN** ระบบตอบกลับ 403

### Requirement: Password sign-in
ผู้ใช้ SHALL ล็อกอินด้วยอีเมลและรหัสผ่าน ระบบ MUST เก็บรหัสผ่านแบบ hash ที่ย้อนกลับไม่ได้ และ MUST ไม่บอกว่าอีเมลหรือรหัสผ่านส่วนใดผิด

#### Scenario: ล็อกอินสำเร็จ
- **WHEN** ผู้ใช้ที่ active กรอกอีเมลและรหัสผ่านถูกต้อง
- **THEN** ระบบออก session และพาเข้าสู่หน้าแรกตาม role

#### Scenario: รหัสผ่านผิด
- **WHEN** ผู้ใช้กรอกรหัสผ่านผิด
- **THEN** ระบบแสดงข้อความ "อีเมลหรือรหัสผ่านไม่ถูกต้อง" โดยไม่ระบุว่าส่วนใดผิด

#### Scenario: บัญชีถูกปิดใช้งาน
- **WHEN** ผู้ใช้ที่ถูกปิดใช้งานกรอกข้อมูลล็อกอินถูกต้อง
- **THEN** ระบบปฏิเสธการล็อกอิน

### Requirement: Brute-force protection
ระบบ SHALL ล็อกบัญชีชั่วคราว 15 นาทีเมื่อล็อกอินผิดติดกัน 5 ครั้ง

#### Scenario: ผิดครบ 5 ครั้ง
- **WHEN** มีการล็อกอินด้วยรหัสผ่านผิด 5 ครั้งติดกันสำหรับบัญชีเดียว
- **THEN** ระบบปฏิเสธการล็อกอินของบัญชีนั้นทุกครั้งในอีก 15 นาที แม้รหัสผ่านถูก และบันทึกเหตุการณ์ลง audit trail

### Requirement: Session lifetime
Session SHALL ประกอบด้วย access token อายุไม่เกิน 15 นาที และ refresh token อายุไม่เกิน 8 ชั่วโมงที่ต่ออายุแบบหมุนเวียน (ใช้ซ้ำไม่ได้) การล็อกเอาต์ MUST ทำให้ refresh token ใช้ไม่ได้ทันที

#### Scenario: Access token หมดอายุ
- **WHEN** access token หมดอายุแต่ refresh token ยังใช้ได้
- **THEN** client ขอ access token ใหม่ได้โดยผู้ใช้ไม่ต้องล็อกอินซ้ำ

#### Scenario: ใช้ refresh token ซ้ำ
- **WHEN** มีการใช้ refresh token ที่เคยถูกใช้ต่ออายุไปแล้ว
- **THEN** ระบบปฏิเสธและยกเลิก session ทั้งชุดของผู้ใช้นั้น

#### Scenario: ล็อกเอาต์
- **WHEN** ผู้ใช้ล็อกเอาต์
- **THEN** refresh token เดิมใช้ต่ออายุไม่ได้อีก

### Requirement: User administration
System Admin SHALL สร้างผู้ใช้, กำหนด/เปลี่ยน role, ปิดใช้งาน/เปิดใช้งาน และรีเซ็ตรหัสผ่านได้ ระบบ MUST ไม่ลบบัญชีผู้ใช้ทิ้งเพื่อรักษาความถูกต้องของ audit trail การเปลี่ยน role หรือปิดใช้งาน MUST มีผลกับ session ที่เปิดอยู่ภายใน 15 นาที

#### Scenario: ปิดใช้งานผู้ใช้
- **WHEN** System Admin ปิดใช้งานผู้ใช้ที่กำลังล็อกอินอยู่
- **THEN** ผู้ใช้นั้นต่ออายุ session ไม่ได้ และประวัติการกระทำของเขาใน audit trail ยังคงอยู่ครบ

#### Scenario: Admin ปิดใช้งานตัวเองคนสุดท้าย
- **WHEN** System Admin ที่ active เพียงคนเดียวพยายามปิดใช้งานตัวเองหรือถอด role `SYS_ADMIN` ของตัวเอง
- **THEN** ระบบปฏิเสธ เพื่อไม่ให้ระบบไม่มีผู้ดูแลเหลืออยู่

#### Scenario: เปลี่ยน role
- **WHEN** System Admin เปลี่ยน role ของผู้ใช้
- **THEN** ระบบบันทึกค่า role ก่อนและหลังลง audit trail

### Requirement: Temporary password change
บัญชีที่ถูกสร้างใหม่หรือถูกรีเซ็ตรหัสผ่านโดย System Admin (รวมถึง System Admin คนแรกที่ระบบสร้างตอนติดตั้ง) SHALL ได้รหัสผ่านชั่วคราว และ MUST เปลี่ยนรหัสผ่านก่อนใช้งานส่วนอื่นของระบบได้

#### Scenario: ล็อกอินครั้งแรก
- **WHEN** ผู้ใช้ล็อกอินด้วยรหัสผ่านชั่วคราว
- **THEN** ระบบพาไปหน้าเปลี่ยนรหัสผ่าน และปฏิเสธคำขออื่นทั้งหมดจนกว่าจะเปลี่ยนสำเร็จ
