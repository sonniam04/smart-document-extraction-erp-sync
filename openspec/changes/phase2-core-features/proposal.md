# Proposal

## Why

Phase 1 วางฐานไว้แล้ว: เอกสารเข้าระบบได้อย่างปลอดภัย, มีสถานะและ audit trail แต่ตัวอ่านยังเป็น provider จำลองที่คืนค่าว่าง ฝ่ายบัญชีจึงยังต้องคีย์ข้อมูลเองทั้งหมด Phase 2 (สัปดาห์ที่ 3–5, 35% ของงานตาม BRD ข้อ 9) ทำให้ระบบอ่านใบแจ้งหนี้/ใบกำกับภาษี/ใบเสร็จได้จริง ตรวจยอดและ Tax ID อัตโนมัติ และให้เจ้าหน้าที่ตรวจแก้บนหน้าจอแบบสองฝั่ง ซึ่งเป็นแกนของ KPI ลดงานคีย์ 80%, ความแม่นยำ >92% และคำนวณถูก 100% (BRD FR-02, FR-03, FR-04)

## What Changes

- **อ่านเอกสารด้วย AI จริง (FR-02):** เพิ่ม provider ที่ส่ง PDF/ภาพให้ Claude vision หรือ Gemini (เลือกด้วย config) แล้วได้ข้อมูลระดับหัวเอกสาร (เลขที่, วันที่, Tax ID และสาขาผู้ขาย/ผู้ซื้อ, ยอดต่าง ๆ, หัก ณ ที่จ่าย) และรายการสินค้าเป็น JSON ตาม schema พร้อมความมั่นใจและตำแหน่งบนหน้าเอกสารราย field รองรับ PDF หลายหน้า, TIFF, JPG, PNG และจำกัดเวลาให้ทันเป้า <30 วินาทีต่อเอกสาร
- **กฎตรวจข้อมูล (FR-03):** ตรวจยอดสองชั้น ชั้นที่ 1 คือ ผลรวมรายการ → ยอดก่อนภาษี − ส่วนลด + VAT = ยอดรวม และ VAT = 7% ของฐานภาษี ชั้นที่ 2 คือ ยอดรวม − หัก ณ ที่จ่าย (คิดจากฐาน WHT แยก) = ยอดจ่ายสุทธิ คลาดเคลื่อนได้ไม่เกิน ±0.01 บาท นอกจากนี้ตรวจ Tax ID 13 หลักด้วยหลักตรวจสอบ, Tax ID ผู้ซื้อต้องเป็นของบริษัทเรา และตรวจเลขที่ใบแจ้งหนี้ซ้ำของผู้ขายรายเดียวกัน ทุกข้อที่ไม่ผ่านจะแสดงเป็นรายการ "ต้องตรวจ" ที่ชี้ไปที่ field ได้
- **หน้าตรวจข้อมูลแบบสองฝั่ง (FR-04):** ฝั่งซ้ายเป็นตัวแสดง PDF/ภาพ (PDF.js) ที่ไฮไลต์ตำแหน่งของ field ที่กำลังแก้ ฝั่งขวาเป็นฟอร์ม 4 หมวดตาม wireframe ที่อนุมัติแล้ว แก้แล้วตรวจยอดใหม่ทันที บันทึกทุกการแก้ไขราย field ลง audit เมื่อ Clerk ยืนยันแล้วจะเปิดใบถัดไปให้อัตโนมัติ
- **ประเมินความเสี่ยงและส่งต่อ (BRD ข้อ 6 Fallback):** หลังยืนยัน ระบบประเมินความเสี่ยง ถ้าความมั่นใจต่ำกว่า 85%, ยอดสูงกว่าเกณฑ์, ผู้ขายใหม่, หรือมีการแก้ยอดเงิน จะส่งเข้าคิวของ AP Lead และห้าม auto-sync ส่วนเคสไม่เสี่ยงจะอยู่ที่ `VERIFIED` รอการ sync ใน Phase 3
- **โหมด AP Lead:** คิวรออนุมัติ, เห็นเหตุผลความเสี่ยงและประวัติการแก้ไข (ค่าก่อน/หลัง), อนุมัติหรือปฏิเสธพร้อมเหตุผล และห้ามอนุมัติเอกสารที่ตัวเองเป็นผู้ยืนยันหรือแก้ไข
- **ทะเบียนผู้ขาย:** สร้างหรือจับคู่ผู้ขายจาก Tax ID + รหัสสาขาเมื่อยืนยันเอกสาร
- **ชุดวัดผล:** ชุดเอกสารทดสอบพร้อมเฉลย และสคริปต์วัดความแม่นยำราย field/รายบรรทัด และเวลาต่อเอกสาร

นอกขอบเขต: การส่งข้อมูลเข้า ERP, ลงลายเซ็น payload, retry/DLQ (Phase 3); OIDC/SSO; production infrastructure (Phase 4); การตรวจกับระบบของกรมสรรพากร

### สมมติฐาน (ให้ผู้ใช้ยืนยันตอนรีวิว)

1. **AI provider มีสองตัวให้เลือก: Claude vision (Anthropic API) และ Gemini (Google Gemini API)** ผ่าน interface `ExtractionProvider` เดิม เลือกด้วย config ไม่ต้องมี OCR แยก — เพิ่ม Gemini ตามที่ผู้ใช้ขอระหว่าง apply (2026-10-29) เพราะระบบใช้ภายในและยังไม่มี Anthropic API key
2. **ขอบเขตรวมการประเมินความเสี่ยงและการอนุมัติของ AP Lead** เพราะเส้นทาง `VERIFIED → PENDING_APPROVAL → APPROVED/REJECTED` เป็นข้อมูลที่ Phase 3 ต้องใช้ในการตัดสินว่าจะ sync อะไร
3. **ตรวจ Tax ID ด้วยหลักตรวจสอบ 13 หลักและทะเบียนผู้ขายภายในระบบ** ไม่เรียกบริการของกรมสรรพากร
4. **ชุดทดสอบเริ่มจากเอกสารสังเคราะห์** (ใบกำกับภาษีไทยจำลองหลายรูปแบบพร้อมเฉลย) แล้วเพิ่มเอกสารจริงที่ปิดข้อมูลแล้วเมื่อได้รับ ไฟล์จริงไม่เข้า git
5. **"Needs Review" ใน FR-03 ไม่ใช่สถานะใหม่** เอกสารที่ตรวจยอดไม่ผ่านยังอยู่ที่ `EXTRACTED` แต่มีรายการ "ต้องตรวจ" และยืนยันไม่ได้จนกว่าจะแก้ จึงไม่ต้องเปลี่ยน state machine ของ Phase 1

## Capabilities

### New Capabilities
- `document-extraction`: การอ่านข้อมูลจากไฟล์เอกสารด้วย AI — field ระดับหัวเอกสารและรายการสินค้า, ความมั่นใจและตำแหน่งราย field, ชนิดไฟล์และจำนวนหน้าที่รองรับ, เวลาที่ใช้, การจัดการเมื่ออ่านไม่สำเร็จ และการบันทึก provider/รุ่นที่ใช้
- `invoice-validation`: กฎตรวจความถูกต้องของข้อมูลเอกสาร — ยอดสองชั้น, อัตรา VAT, Tax ID, ผู้ซื้อ, เลขที่ใบแจ้งหนี้ซ้ำ และผลการตรวจที่ชี้ไปที่ field
- `risk-assessment`: การประเมินความเสี่ยงหลังยืนยันและการส่งต่อเอกสารเข้าคิวอนุมัติหรือรอ sync ตามเกณฑ์ที่ตั้งค่าได้
- `document-review`: การตรวจแก้ข้อมูลบนหน้าจอสองฝั่งโดย Clerk และการอนุมัติ/ปฏิเสธโดย AP Lead รวมถึงทะเบียนผู้ขายที่เกิดจากการยืนยัน

### Modified Capabilities
- (ไม่มี — `document-lifecycle`, `audit-trail`, `user-access` และ `ui-design-system` ครอบคลุมพฤติกรรมที่ Phase 2 ต้องใช้แล้ว เช่น การเปลี่ยนสถานะ `EXTRACTED→VERIFIED→PENDING_APPROVAL`, audit การแก้ field ค่าก่อน/หลัง และการแสดงความมั่นใจ)

## Impact

- `sdes-service` (`Service/`)
  - `packages/core`: schema ของผลการอ่าน, กฎตรวจข้อมูล, กฎความเสี่ยง (ไม่ผูกกับ framework, unit test ได้ตรง)
  - `apps/worker`: provider Claude, แปลง TIFF เป็นภาพ, ตรวจข้อมูลหลังอ่าน
  - `apps/api`: endpoint อ่าน/แก้ข้อมูลเอกสาร, ยืนยัน, คิวอนุมัติ, อนุมัติ/ปฏิเสธ, ลิงก์ดูไฟล์ต้นฉบับ
  - `packages/db`: migration เล็กน้อย เช่น ผลการตรวจ, ผู้ยืนยัน และ unique ของผู้ขาย + เลขที่ใบแจ้งหนี้
- `sdes-web` (`Web/`): หน้า `/documents/[id]` (split-view + PDF.js), คิวรออนุมัติ และเชื่อมจากคิวเดิม
- Repo หลัก: ชุดเอกสารทดสอบสังเคราะห์และสคริปต์วัดผลใน `qa/`, ขยาย E2E
- Dependency ใหม่: `@anthropic-ai/sdk`, `@google/genai`, `pdfjs-dist` และตัวแปลงภาพ (`sharp`)
- Secret ใหม่: `ANTHROPIC_API_KEY` และ/หรือ `GEMINI_API_KEY` (ใน `.env` เท่านั้น)
- ข้อมูลเอกสารถูกส่งไปประมวลผลที่ผู้ให้บริการ AI ภายนอก ต้องใช้บัญชีที่ไม่นำข้อมูลไปฝึกโมเดล และบันทึกเรื่องนี้ไว้สำหรับการประเมิน PDPA — **Gemini free tier ไม่ผ่านข้อนี้** (Google นำข้อมูลไปปรับปรุงผลิตภัณฑ์และอาจมีคนอ่าน) ต้องใช้ paid tier
